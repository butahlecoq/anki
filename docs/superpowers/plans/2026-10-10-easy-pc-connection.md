# Automatic private PC connection implementation plan

> For agentic workers: use superpowers:executing-plans to implement this plan task by task. Issue #327 is the specification. Execute inline; independent Matt Standards and Spec agents review the final head.

The owner requests no address/code step. Use the existing private proxy's authenticated owner identity to establish the existing device credential, then retain normal sync and AnkiWeb username/password. The configured private flow connects automatically on app entry. No automatic collection exchange occurs.

1. [ ] Add a public HTTP tracer test in `server/private-connection.test.ts`: configured owner discovers connection capability, POST connects without code, issued credential accesses an authenticated endpoint. Run it red before implementation. Add missing/wrong identity, wrong Origin, disabled configuration, invalid/oversized body, and revocation rejection coverage as vertical slices.
2. [ ] Implement the small authorization boundary in `server/private-connection.ts`, route it from `server/sync-http.ts`, reuse device-credential issuance in `server/sync-service.ts`, and pass the explicit trusted-proxy owner setting through `server/index.ts`. Require loopback binding and configured app Origin; default disabled. Existing manual pairing and token authentication remain supported.
3. [ ] Add public client tests around same-origin capability discovery/connection in `src/sync-client.test.ts`. Preserve settings, collection generation, local records and pending work on failure; reuse existing credentials. Implement the client interface without a user-supplied address or code.
4. [ ] Integrate automatic connection and retry states in `src/SyncControls.tsx` and account setup in `src/AnkiWebAccountDialog.tsx`. Test actual UI fields/focus, pending state, successful connection, failed connection and retry. Manual pairing is advanced for other topologies, never the configured private-flow error fallback.
5. [ ] Add a real-browser test with a synthetic identity-injecting loopback proxy and actual PC service, not application-response mocks. Verify fresh connection, persisted reopen, local-note preservation, no code/address input, and direct AnkiWeb fields. Retain existing sync/account/download/offline journeys.
6. [ ] Document setup and trust in README and ADR; keep actual owner identity and credentials out of source/logs. Prove the deployed private proxy supplies authenticated identity before enabling the option.
7. [ ] Commit and pin the source. Run focused tests and full literal `npm run check` with `ANKI_TEST_PYTHON`, `KIROKU_ANKI_COMPAT_PACKAGE`, separate `KIROKU_WEB_PORT`/`KIROKU_SYNC_PORT`, and `KIROKU_RELEASE_QUALIFICATION=1`. Hosted complete gate and fresh independent Matt reviews must pass on that exact head.
8. [ ] Archive failures/results/source, record acceptance, run premerge, protected merge and same-step disposable worktree cleanup. Then deploy qualified artifacts with fresh backup/rehearsal, verify actual private-origin automatic connection and original rows/media, and record delivery. Phone testing is non-blocking by the owner's explicit instruction.

Validation must distinguish authenticated private connection from merely being on a tailnet. A configured owner match, trusted loopback proxy and exact Origin authorize credential issuance. Later requests still authenticate through revocable device tokens. Connection stores only that credential and endpoint; account passwords remain in memory. Failed setup must not erase or overwrite local study work.
